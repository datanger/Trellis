# Trellis execution protocol (normative)

The human owns goals, approved design/contract, evaluation truth, risk acceptance and release. The coding agent owns implementation. Deterministic tools record the decisions and actual test evidence. This protocol is the workflow owner; a selected upstream skill supplies a bounded capability, not a competing lifecycle. Host/system instructions, user permissions, and stricter project constraints still apply. Never use this document to bypass host sandbox, permission or policy checks.

## 1. Resolve intent and route

Use the eight stable entry names and natural-language task text. Find the real project root and applicable project instructions. The user need not see internal route names. Run the CLI in that root (`T` below denotes `<installation Python 3.9+> /absolute/toolkit/trellis.py --project /absolute/project`, not a shell alias that is automatically installed).

- `T catalog <entry>`: list all task templates for this entry. Select semantically using the user request, available context and examples. Use `T compose <entry> --route <entry.route> [--route ...]` to preview. For combined work, order templates by prerequisites and preserve required gates. Do not run overlapping templates blindly. If a user explicitly requests a specific upstream capability, inspect `registry/coverage.json` / `upstream-capabilities.json`; route to its canonical family and use unique complementary instructions when applicable. Cross-entry work is redirected to the proper entry, not silently executed as a different operation. For an unusual task compose existing applicable capabilities; do not invent a fake upstream skill.
- Check `T status`, Git working tree and actual artifacts. Resume an existing active run using `T next W-...`, rather than duplicate it. If state is absent and initialization was not requested, ask permission to initialize the minimal metadata/docs or do the requested read-only inspection without claiming a managed Trellis workflow. `T start` may create workflow metadata for a new project, but does not overwrite existing files.
- `T start <entry> --route <id> --request '<original task text>' --scope <stable ID> --allow <path> ...`. Scope normally matches a functional ID or module and must remain stable across design, contract and implementation. `--allow` is an explicit relative path or directory, repeatable. For mutating dev/contract/simpler routes it is required. Do not quietly extend it; cancel/replan with the user if scope expands. Read-only audit should not alter product files. Local reports and temporary reproduction harnesses under `.trellis/` are allowed when requested; do not write remote systems.

## 2. Capture requests at every entry

When the user makes a real new, modified or deleted product requirement, call `T raw-add --text '<exact original>' --source '<conversation turn or original document + section/page/date>' [--operation modify|delete --supersedes R-0001]`. Use `--text-file` for long excerpts. Preserve the source file/reference. Do not record a tentative question or AI inference as a user instruction. Review newly captured items before ending a session. The runtime does not intercept chats outside the eight entry skills: install the project rule block for ordinary agent conversations as well. Unavailable prior conversation or attachment contents must be requested, not fabricated.

Use `T functional-upsert --category 'File processing' --text '...' --raw R-0001 --acceptance '...' [--derived] [--id F01-001]`. Categories and IDs remain stable. Newly created/modified functions are proposed, not confirmed. Present concise delta, raw IDs, acceptance and effect on accepted modules. On approval use `T confirm-functional --id F01-001 --gate G-... [--cancel]`; cancellation preserves the ID/history. The gate must include the functional requirements document and scope. For a project-wide approval, list all approved F IDs in the summary and confirm only these. An AI inference remains pending until the user explicitly accepts it. Do not overwrite past raw records or delete history. Affected downstream approvals become superseded. The two Markdown views are generated from internal state; if edited by hand stop and reconcile explicitly, never overwrite them. Do not maintain a second independent Spec Kit requirements truth; detailed feature specs reference R/F IDs.

## 3. Execute the persistent workflow

Repeat for each current step:

1. Run `T preflight W-...`. It returns the current task, actual pinned provider files, gates, and checks scope/prerequisites/baselines. If blocked, stop and explain; do not run ad hoc steps around the check. `T next` is inspection only.
2. Read each relevant **actual provider file** and its applicable references from the returned repository root. Use `T deps resolve '<provider>:<path>'` for additional registered resources; read reference paths under that checkout, not a guessed path in the target repo. Apply adapter rules below. If a provider is missing, report the blocked capability and use `deps sync` only with approved network installation. Never pretend a provider was invoked. Avoid running duplicate full workflows: first provider is the main method for that step; others supplement missing details. The upstream catalog is pinned, not auto-upgraded.
3. Execute the step using host tools: read sources, edit only allowed paths, run the actual test framework/browser/CLI as required. For read-only audits do not run destructive or modifying provider steps. Preserve existing uncommitted user changes. Store concrete evidence under `.trellis/reports/` or an existing appropriate document, not a new long report for every trivial task. For code changes include diff, actual test command/results and changed document references.
4. For ordinary work: `T complete W-... --evidence <relative-file> [--evidence ...]`. Use evidence tied to the action, not an empty file. For verify steps: run the approved command through `T test --timeout 300 -- python -m pytest ...` (argv, no shell parsing), then `T complete W-... --receipt .trellis/receipts/T-....json --evidence <report-or-receipt>`. For multiple required commands run each, verify every exit status and include all receipts as evidence; one successful receipt cannot substitute for other required checks. Test failure blocks advancement. A receipt records actual exit code and code-tree hash, not semantic proof that the test suite is adequate. If a command generates tracked/untracked artifacts that change the measured tree, separate preparation from test execution and ignore only approved generated artifacts; never suppress meaningful diffs. Do not choose a no-op command to get green.
5. For a gate step, follow section 4; no automatic completion. `T complete` checks the gate is approved for the same run and step. For a failed/rejected step revise evidence, propose again or cancel/replan. Do not make an endless retry loop; stop after the approved bound, or three rounds without measurable progress by default.
6. When done, summarize actual results, unresolved risks and the next required human decision. Do not mark implemented code accepted before the acceptance gate and baseline. `status` reports discrete states, not invented percentages.

The engine does not launch model agents independently. The host agent interprets intent, reads provider instructions and executes tool calls. It is not a trusted sandbox or independent proof of semantic completion. State, files and tests remain editable by an authorized shell; use separate human-controlled CI and repository protection for enforcement.

## 4. Human approvals

Each gate binds exact existing review artifacts to a SHA-256-based review token. Prepare the minimum useful packet: current result, diagram/real example, alternatives or risk, what changes, what does not, exact files, test criteria, next action. Run:

```
T propose --run W-... --scope F01-001 --stage design \
  --file docs/design/architecture.md --file docs/design/technical-design.md \
  --summary 'Review architecture and core algorithm; no implementation yet'
```

Show the returned gate ID and token. **Stop** at this point. Ask for a clear decision. The user may run `T decide G-... --token <token> --by '<reviewer>' --decision approve` from their terminal, or explicitly approve that exact packet/token in chat and authorize the agent to record the decision. Never generate approval because a provider asks, infer approval from silence, fabricate a reviewer, or treat an earlier unrelated approval as current. Rejected/stale packets must be re-proposed. After explicit approval, `T complete W-... --gate G-...`. The token detects artifact changes; it is not an authentication secret or cryptographic signature. For tamper-resistant approvals, use GitHub required reviews or separate human-controlled signing/CI.

For major new features the order is requirements → design → interface contract → code skeleton → skeleton integration → plan → dev → acceptance. `contract.progressive` has distinct gates, not one combined review. Use the same scope. Store current design, contract and skeleton **public signatures/structure manifest** as review artifacts; don't bind mutable implementation bodies to the skeleton gate needed for subsequent work. Use actual source paths/diff as evidence, and check public signature drift in CI. For existing projects first adopt the current design and baseline; small bugs use a bounded defect change gate, not a forced rebuild of every document. Approval covers only named artifacts, scope, risk and test criteria.

## 5. Protect accepted work

Before any dev/cleanup/contract change run `guard` and inspect Git diff. Use protected main, small feature branches or optional worktrees, atomic commits and review. Never force push, reset user changes, or auto merge/publish. All accepted behavior, public contracts, approved design docs and evaluator inputs should have protected paths and actual regression tests.

If a protected file needs an intended change, first propose a `change` gate containing a short change plan, old protected files, affected requirements, rationale, compatibility, tests and rollback. Obtain explicit approval. Run `T authorize-change W-... --gate G-... --file path ...` **before** modifying them. It grants only exact named files for that active run. Gate artifacts other than mutable target files remain authoritative; no arbitrary edits outside permitted scope. Any change to protected acceptance truth needs separate review by the evaluator owner. The ordinary `guard` remains failing until fresh re-acceptance; a temporary work grant is not release approval. The runtime does not yet enforce deletion/renaming of previously protected paths; deliberately retire or migrate an old protected file via a reviewed project-state migration, not by silently removing it from the manifest.

Before implementation, write a machine-readable acceptance policy (e.g. `contracts/acceptance/F01-001.json`) containing `commands` (nonempty arrays of exact argv strings) and `protect` (project-relative files to protect). Include it in the plan or evaluation approval. After implementation, commit the reviewed source/docs/tests (exclude `.trellis/` metadata from the code-tree cleanliness check). Run actual approved tests on that unchanged committed tree. Create acceptance proposal including exact protected files and **all** test receipts; obtain approval. `T baseline --scope ... --gate ... --policy contracts/acceptance/F01-001.json --receipt .trellis/receipts/T-...json --file ...` stores Git SHA, file hashes and receipt hashes and requires a passing receipt for every approved policy command; the policy itself and its protected paths must be included. A later code change must either preserve accepted files or go through change authorization, regression and re-acceptance. Shared paths require re-acceptance for every affected baseline. Commit metadata and receipts separately. Keep full local test logs as evidence; review/sanitize before sharing, they may include secrets. Guard checks only explicitly protected files, not all behavior or undocumented dependencies. Use actual contract and integration tests for hidden interactions. For CI, run `python3 /trusted/toolkit/trellis.py --project . guard` in addition to existing protected test commands; source/CI/acceptance changes must receive independent approval. Do not let the implementation agent own the independent evaluator or protected branch settings.

## 6. Provider adapter rules

- **Superpowers**: read selected `skills/.../SKILL.md`, its references and applicable platform adapter. The process owner is Trellis. `using-superpowers` and `using-agent-skills` inform discovery, not global auto-injection. Use TDD red/green with meaningful failing test, system debugging for failures, verification for proof. If subagent or parallel tools are absent, say so and obtain approval to use sequential equivalent; no invented subagent review. Do not run full competing planning or automatic branch finishing. Follow project Git authorization.
- **Spec Kit**: pinned source includes raw templates (`templates/commands/*.md`) and official bug/assess extension command templates. Their `{SCRIPT}`, `$ARGUMENTS`, `__SPECKIT_COMMAND_*__`, feature directories and hook substitutions are **not executable shell commands**. For Trellis-managed work, use the method and template semantics with the current user text, R/F IDs and Trellis artifact paths; adapt the method explicitly, do not run unresolved placeholders or duplicate requirements/state. Native commands, hooks, presets, overlays, bundles, catalogs, workflow steps/functions, artifact inventory, integration/admin operations require the pinned Specify CLI and its initialized native project. Inspect `docs/installation.md` and the relevant native command docs, use `specify --help` and actual installed integration output; never claim native execution from reading a template. With explicit user approval install pinned CLI from the checked-out repo (`uv tool install --from <pinned-spec-kit-checkout> specify-cli`, confirm current syntax via `uv` help); create/use a separate authorized native workspace if it would conflict with Trellis docs or expose extra commands. Use official bug/assess extensions only from pinned checkout / approved sources; preserve output and map to R/F and gates. Report missing `uv` or unsupported native command as blocked. Don't silently install community catalogs, execute lifecycle hooks, or move the target project's branch.
- **Ponytail**: load selected pinned prompt (ordinary, diff review, repo audit, debt, gain, help). Trellis policy `lite/full/ultra/off` selects intensity; `off` disables simplification advice, not project quality or safety requirements. Set `T policy <mode>` only on explicit request. Avoid needless code, reuse, and preserve reasonable abstractions; code count is not a quality objective. Native Band/telemetry/import is host-specific, may contain private session data, and requires the supported native plugin and explicit permission. Do not activate session hooks or read/import histories unasked; if absent report blocked, not fabricated cost data. Author benchmarks are not local measurements.
- **Archify**: read the actual `archify/SKILL.md`, relevant schema/example and reference; run its real Node CLI from the pinned skill root with explicit target repo and artifact outputs. Use real repository evidence and run native finalize/validation/delivery/browser checks for the chosen type; follow its bounded repair instructions. Architecture, workflow, sequence, data flow, lifecycle, ERD, class, tree, timeline, waterfall, explainer/story, exports, diagnosis, delta, preview and PR visualization are routed separately. SVG output is preferred for Markdown when available; preserve editable source and actual HTML/receipt if applicable. Do not invent diagrams, render output or claim visual validation without executing. Respect optional analysis/PR attach approval, update notice (never self-update), and exact PR commit range. No remote attachment without approval. If native renderer or browser unavailable, report the capability blocked; use a clearly labeled textual fallback only if user accepts it.
- **Agent Skills**: load selected skill and repo-level `references/` or `agents/` persona as appropriate. Use independent review where supported; five-axis review and complementary safety/performance/accessibility/observability checklists are retained, not repeated full workflows. Browser testing uses actual DevTools/browser, not imagined screenshots. Native command wrappers are references; when a specific native command is requested read the pinned command file and run only through supported host/integration. Do not grant external permissions or install tools automatically.
- **Upstream-maintainer-only skills**: registered but only run when the explicit target is that upstream project or its authorized clone. Mirrored files are de-duplicated. A direct request for a unique method inside a merged capability uses its actual upstream source as complementary input. Do not discard distinct semantics just because two method names overlap.

If external docs demand an incompatible workflow, keep Trellis's stricter human approvals, scope, protected tests and state. Document the adaptation. For unavailable native capabilities report `blocked` and the needed environment, or ask permission to use an alternative. No fake results, no silent fallback. The five repositories' source files stay in private `upstream/` clones, outside host skill discovery. Existing separately installed provider plugins/hooks may still auto-trigger; for predictable use disable overlapping workflow injection in that host or scope, with user approval. Trellis cannot turn off other plugins automatically.

## 7. Task-specific delivery

- Algorithm: fixed evaluator/data split, baseline, hypothesis, small experiment, logs, bounded iterations, final independent evidence. Do not optimize on holdout or alter truth. Plan mode for metrics/design; use native Goal mode if supported only with clear authorized limits and stop condition. Otherwise run bounded iterations in normal host session.
- Frontend: user-approved prototype, component reuse, contract/fixture, actual browser and visual/interaction/console evidence. Human owns visual judgment; screenshot diffs do not prove aesthetics.
- Backend: contracts, schema, concurrency, idempotency, timeout/retry, errors, security, real integration and migration rollback. No irreversible data operation without approval.
- Audit: findings with severity, exact source path/line, actual evidence, reproduction or uncertainty, and suggested action; do not modify business code.
- Simpler: baseline tests first, prove unused/redundant content before removal, small changes, regression; preserve design intent, raw requests, decisions and accepted behavior. Document cleanup must reduce reading cost and keep one current explanation; keep required history in Git.

## 8. User-facing report

Use a short decision packet: **Current outcome** (what happened), **Evidence** (files/commands/real examples), **Decision needed** (what must be judged and options/tradeoffs), **Next automatic action** (what will follow approval). If no decision is required continue automatically within the authorized scope. Keep project status truthful and explain actual mechanisms in accessible language, not an encyclopedic file/class inventory. Use diagrams for understanding, not decoration.
