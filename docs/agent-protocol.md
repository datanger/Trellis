# Trellis shared rules (read only the relevant sections)

Trellis selects capabilities; the host agent plans and executes. Do not create a second workflow engine. Follow user/host permissions and project instructions. Do not invoke every provider or create a report per step. If a provider is unavailable, say what is blocked; do not pretend it ran.

## Route
Identify intent, scope, risk and expected outcome. Read the selected entry's `skills/trellis-<entry>/workflows.md` and relevant sections only. Its task-specific rules name actual upstream resources, required calls and conditional calls. These are the default method, not optional suggestions. For unmatched or specialized tasks use `python3 <toolkit>/trellis.py catalog <entry>` to find the exact source(s), including native and complementary capabilities; cross-entry selection is internal if consistent with the request. The user need not know provider names. Explicit user constraints take priority over defaults, without weakening verification or safety.

Before the corresponding action, resolve each required/applicable source with `deps resolve <source-key>` and read the actual pinned file and relevant references and `docs/providers/<provider>.md`. Never rely on the name alone or substitute a remembered summary for reading it. Use one primary process and add only distinct complementary methods; do not repeat entire overlapping lifecycles. A missing required resource blocks that method; report the precise blocker or use an explicitly authorized fallback without claiming it was run. Native templates, plugins and scripts require actual supported prerequisites; adapting a method is not native execution.

For substantive code implementation, load `ponytail:skills/ponytail/SKILL.md` automatically before writing (default full unless explicitly overridden). Use its smallest complete change, reuse, scope and test constraints throughout. It does not authorize reducing required behavior or changing approved contracts. Reuse an accessible existing plan, including host-native `/plan`; do not duplicate planning or demand a special plan format. Follow Superpowers execution/test methods as applicable, with authorized host tools; do not import a second workflow engine. For plan-only or read-only tasks do not implement code.

## Human control
Small reversible changes: execute then verify, no extra approval unless requested. Ordinary scoped features: plan briefly, implement and test within authorized scope. Major new or cross-module features: confirm requirements, design, interface/examples, public skeleton, then validate skeleton integration before business implementation. Confirm the module plan and acceptance criteria when consequential. Each distinct decision is reviewed before proceeding; do not pre-generate all later designs before approval. Approval may be explicit in chat. For major decisions record scope, decision, date and reviewed Git revision or artifact in the existing design/plan or a short project decision log; no tokens or per-step receipts. A material change invalidates the relevant approval, not unrelated work. Resume from Git, current docs and outstanding decisions, not a private cursor. Record a short handoff for long tasks only. See `docs/progressive-development.md` for complex stage boundaries and module implementation/acceptance cycles.

## Requirements
Read `docs/requirements-rules.md` only for new/changed/deleted product requirements. Capture across all entries; an invocation, test request, question, temporary operation or AI suggestion is not automatically a requirement. Markdown is canonical and directly editable. No state.json writes or generated views. Use the two numbered-list documents (functional numbering restarts in each category). For old tables, bullet lists or v0.1 state, use reviewed migration, not bootstrap overwrite.

## Verification and protection
Read `docs/verification.md` for code changes, testing or acceptance. Real tests and Git diff are evidence; no custom receipt wrapper. Preserve existing changes. Protect accepted behavior, public contracts and independent evaluation criteria, not every file byte. For protected interfaces, evaluator truth, destructive actions or material design changes obtain explicit approval before changing. Do not weaken tests or alter data splits to make results pass. Independent CI and required reviews enforce policy; Skill instructions alone do not. Never automatically commit, merge, push, publish, attach PR assets or install unrelated tools without authorization.

## Reporting
Return outcome, actual evidence, unresolved issues, and only the decision needed now. Never claim unrun tests passed. Use concise, human-readable documents. Briefly report the actual upstream resources used and blocked where relevant; distinguish loaded/adapted instructions from native execution. No redundant execution logs or compulsory status files.
